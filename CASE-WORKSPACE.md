# NAVO case workspace

Adds Case workspace and Case search beside the existing modules. The initial case types are Observation, Accident, Near miss, Inspection, Audit, Audit finding and Meeting.

## Included

- Folder catalogue and personal bookmarks; project selection creates a private database draft.
- Left section stepper with tab / scroll views, required-field validation, hierarchical risk and department pickers, complete supplied risk taxonomy and existing cause / checklist libraries.
- Automatic draft saving with revision comparison. Failed saves remain open; a stale browser cannot overwrite another user's changes.
- Potential and actual consequence sliders, cost totals, involved people, investigation classification and causes, PTW and other published checklist templates.
- Actions with all six types, assigned directory users, original deadlines and server-side deadline justification history. Submitted actions use the existing evidence, verification and closure workflow.
- Private project attachments in the existing `photos` bucket, links, immutable comments and authenticated signature declarations tied to a case revision.
- Related / superior / subordinate links to registered workspace cases; numbered read views and printing.
- Search includes both workspace cases and existing NAVO reports / inspections without duplicating projected records. Existing records open their original processing module.
- Project/type/status/date/department/person filters, list/table modes, CSV export, and personal saved searches stored in the signed-in user's browser.
- Home widgets for case types, due status, the user's reports and assignments, drafts and saved searches. Dates and deadlines use Riyadh time.

## Database and deployment

Applied to the connected NAVO project on 13 Oct 2026. For another environment, apply `supabase/migrations/20261013093525_navo_case_workspace.sql` before deploying the new static files. This additive migration is safe to run twice. It creates four RLS-protected tables (`navo_cases`, `navo_case_notes`, `navo_case_links`, `navo_case_medical`) and adds action type / original deadline / justification fields.

Drafts are creator-private even to other HSE users. Registered cases are project-visible; only Admin/HSE can edit them. Comment and signature authors and timestamps are generated by the server. Personal medical details use a separate Admin/HSE-only table; only injury classification and total lost days feed the original KPI records.

Observation / incident cases project transactionally into `reports`, inspections into `inspections`, and case actions into `actions`, using the caller's existing RLS permissions. Audit, audit finding and meeting cases are stored in the workspace. Case processing and the detailed operational source workflow are separate; original records use their original module. No existing records are rewritten by the migration.

Attachment limits are checked in the browser at 50MB; the existing bucket's configured limits still apply. File paths retain the existing project prefix and Storage policies. Draft discard removes the draft record; previously uploaded files remain in private Storage for later administrator cleanup.

## Validation

From a clean checkout:

```sh
npm --prefix tests install
npm --prefix tests exec playwright install chromium
npm --prefix tests test
```

`cases-core.cjs` checks due boundaries and form rules. `cases-sql.cjs` applies the original schema, all old migrations and the new migration twice to a disposable PGlite PostgreSQL database, then checks seven submissions, source projections, project/draft isolation, signatures, protected medical data, revision conflicts and deadline justification. Auth and Storage schemas are minimal fixtures; no production user data is used.

`cases-ui.cjs` runs the actual app in Chromium with a fixture case API. It exercises all seven forms, required validation, hierarchical selection, sliders, action assignment, attachment, comments, signatures, search and mobile layout. It does not prove live Supabase Auth, Storage uploads or Vercel deployment. Optional `CHROME_PATH`, `PLAYWRIGHT_PATH` and `PGLITE_PATH` support locally bundled runtimes.

## Remaining specification items

This is the first case-workspace implementation, not a full Synergi clone. The remaining catalogue folders are explicitly marked planned. Email notifications / share delivery, signature requests, saved company reports, dashboard report widgets, Bowtie views, complete organisation-tree administration, full injury sub-records, detailed loss matrices and the full personal dashboard widget set are not implemented. Department and location pickers use the current project plus NAVO's department list. Personal signatures are recorded declarations, not certificate-based digital signatures.

Existing dashboards, operational modules and exports remain available. Screenshots were not supplied, so visual styling follows the written specification's colours and layout rather than a pixel-for-pixel comparison.
